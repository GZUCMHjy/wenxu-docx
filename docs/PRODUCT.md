# 文序产品目标与需求定位

基线日期：2026-09-21。状态：v0.6 需求基线；当前增量实现与验收边界见 [实施记录](verification/v06.md)。本文面向产品、研发与验收人员。

## 1. 为用户完成什么

文序帮助用户调整已经写好的 Word 文档。用户可以点击按钮统一正文格式，也可以选中一处文字或描述某个栏目，只修改需要的格式，获得可继续编辑的 Word 文件。

核心使用场景是教案等已有业务文档中的反复格式修改：文件中可能同时存在普通段落、表格填写区、图片、公式与批注，用户希望精准修改并保留原稿的其余部分。

产品价值由三个结果决定：范围找得准、要求改得对、其他部分保得住。自然语言和模板用于减少操作成本，常用格式调整必须能直接通过前端控件完成。

## 2. 两条并列主路径

| 路径 | 用户表达 | 应有结果 |
| --- | --- | --- |
| 全局调整 | 正文统一宋体小四，其他控件保持原样 | 只调整被确认属于正文的对象及指定属性，范围和排除项可见 |
| 局部调整 | 将“教学目标”栏的填写内容改为黑体五号 | 找到具体填写区，保留栏目标签、相邻单元格和其他格式 |
| 组合调整 | 正文宋体小四，但第三段字体为黑体 | 第三段黑体小四，其余正文宋体小四；按属性合并 |
| 继续调整 | 在上次结果上只改行距 | 保留已经得到的字体、字号和局部结果，另存新版本 |

全局表示“指定类别或范围内统一调整”，不等同于每次修改整个文件。正文、标题、表格文字、指定片段和保护区都有明确范围，用户可以查看并纠正匹配结果。

## 3. 必须守住的编辑语义

1. **未指定就保持。** 不自动改文字、不润色、不补齐其他格式。控件当前值与本次目标值分开；混合格式不套默认值；加粗等控件支持保持、开启、关闭。
2. **全局和局部共用一套计划。** 同批次的明确局部例外按属性覆盖对应全局设置；同一目标属性仍有歧义时显示冲突，不随机选值。
3. **每次修改基于明确版本。** 旧局部结果不会因新一轮无关属性调整而丢失；用户后续明确全局修改同一属性时，可以覆盖历史局部结果，显式保护或排除的区域除外。
4. **定位和影响范围可见。** 重复文本需要消歧；只选几个字却设置段落行距时，显示其作用于整个段落。页码只用于预览导航，修改绑定版本与文档对象。
5. **保存原稿，输出新版本。** 支持预览、撤销、继续修改；失败不覆盖原稿或已有版本，未完成项不掩盖在总体成功提示里。
6. **检查结果真实。** 目标属性、未指定部分和对象保全独立校验；渲染完成与人工版式复核分开记录。

修改字号、字体或行距可能自然引起重新换行和分页。工具应展示这些变化，不能为了保持页数而擅自缩字、删内容或修改其他属性。

## 4. 本阶段范围

| 范围 | 定位 |
| --- | --- |
| P0：全局与局部格式闭环 | 全局控件、搜索和局部选择、文字要求统一解析、修改清单、明确冲突、精准执行、预览、导出、撤销与继续修改 |
| P0：真实场景必要基础 | DOC 原格式副本与独立核对；表格栏目定位；批注、公式、图片、合并关系等对象的保全验证；未指定属性保持 |
| P1：扩展格式与重复使用 | 个人格式预设、参考/批注规则提取增强、编号整理、表格布局与分页属性、页眉页脚格式等，逐项定义和验收 |
| 后续独立评估 | 多文件批量处理、组织规范发布和跨会话持久化等；不作为当前 P0 前提 |
| 当前范围之外 | 正文生成或润色、业务内容审核、教学质量判断、课程名称或必填内容检查、复杂文档合并 |

v0.6 已加入 DOC 原格式编辑和经过验证的复杂对象保全子集，原格式核对和客户端兼容性仍按独立状态检查。某类对象的“可读取”“可原样保留”“可修改”必须分开声明；文件无法可靠读取、关系无法保全或请求超出支持能力时，阻止对应操作并说明原因。

## 5. 与现有 v0.5 的关系

v0.6 保留“用户自己的稿件、只改确认属性、保留原稿、检查后交付”的基础，补充两条更直接的操作路径和更精确的对象定位。

| 当前 v0.5 POC | v0.6 目标 |
| --- | --- |
| 文字要求或参考实例生成规则核对表 | 增加无需提示词的全局控件和局部选择入口，全部入口共用编辑协议 |
| 角色和段落层的格式规则 | 扩展到字符片段、表格栏目与单元格等实际对象 |
| 普通 DOCX 的受控结构；部分复杂对象预检拒绝 | 增加 DOC 原格式编辑与真实教案复杂对象保全，按验证通过的能力开放 |
| 按范围和属性组织规则 | 对实际重叠对象逐属性合并，形成冻结后的唯一执行计划 |
| 已有有限 XML 修改、校验、Linux 渲染 | 保留这些基础，补定位、复杂对象能力和独立的视觉复核状态 |
| 会话内版本记录 | 保留原稿/输入版本/计划/结果的来源关系；跨会话恢复另行实现 |

详细代码映射、模块契约和实施次序见 [架构设计](ARCHITECTURE.md)。这些逻辑层第一阶段放在同一个 Python 应用中，后续只有出现明确运行需求时再拆服务。

## 6. 如何判定真实场景可用

全局调整覆盖准确，局部调整定位准确，二者都只改变明确指定属性，并通过 [V06-A01 至 V06-A14](REQUIREMENTS.md) 中对应场景。

产品编译、运行和自动化检查统一在 WSL/Linux 中进行。真实文档要检查内容、格式、对象保全和前后页面；Word/WPS 实际打开与继续编辑属于客户端兼容性验收，不能用 Linux 渲染或合成文档结果替代。

交付必须区分已验证、待复核、未支持和失败。只有前端按钮、只有可导出文件，或只有架构图，都不足以证明本阶段目标完成。


### 2026-09-22 原格式保真契约

用户已选择保真优先，输出保留上传格式。DOC 不再强制转换为 DOCX；原格式工作副本在无修改时须与上传文件字节相同。DOC 的原生修改只接受冻结计划中的目标属性，重新打开保存结果并核对全文、范围外格式、批注关联、关系、媒体与 OLE 流；失败不登记版本。DOCX 保持现有最小补丁路线。架构图中的读取、建模、执行、校验与交付职责保持不变，精确修改引擎按原格式分派。
