# 可插拔 WPS / LibreOffice Windows 桌面版：技术方案

状态：技术评估与开发计划，尚未实现或验证新的运行引擎。

日期：2026-09-22。

分支：`feature/standalone-document-engine`。

基线：`lts/windows-desktop` / `72105a6abae03ba3ed5039626feddf6c5d42f5b7`。

## 1. 建议与边界

按用户确认的方向，沿用现有 Qt 桌面和文序修改核心，**通过统一接口接入 WPS 与 LibreOffice 两个引擎：默认优先使用本机可用的 WPS，没有可用 WPS 时使用随包内置的 LibreOffice；用户也可以手动选择。** LibreOffice 随应用交付，因此不需要预装办公软件、Python 或 WSL，也不需要联网处理文档。

这是有验证条件的技术选型。LibreOffice 官方提供免费开源的 Windows 便携形态，也有 DOC、DOCX 和 PDF 过滤器；这些资料支持开展验证，**不能证明已有稿件经其编辑保存后仍与 WPS 显示完全一致**。[S1][S2]

用户已经明确的约束：

- 新增的内置引擎必须免费开源，排除付费 SDK、试用水印和云端转换服务；本机已有 WPS 仍可作为可选引擎使用，不随本产品分发 WPS。
- 提供“自动（优先 WPS） / WPS / LibreOffice”三种选择，默认自动，显式选择优先于自动策略。
- 保真优先，DOC 输入仍输出 DOC，DOCX 输入仍输出 DOCX。
- 没有有效修改时，直接保留原始字节；不通过重新保存生成工作副本。
- 原稿不覆盖；私有附件及其转换文件、截图、抽取文本只作本地验证，不进入 Git、远程 CI 或发布包。
- 本轮只建分支、梳理方案和验收计划，不修改业务代码。

最先验证两个问题：**完整便携包能否在干净 Windows 上离线运行；DOC 保存能否保住公式、对象与非目标格式。** 两项未通过前，不把桌面业务大规模迁移到新引擎。

### 默认选择与手动切换

这里的“有 WPS”指可用性探测通过，包括自动化接口和必要操作能力，而不只是磁盘上存在安装目录。探测应有超时且不操作用户文档；注册信息只是线索，当前已有实例占用等无法安全启动的情况也需要明确返回原因。

| 用户偏好 | 打开文档前的检查结果 | 实际行为 |
| --- | --- | --- |
| 自动（首次默认） | WPS 可用 | 使用 WPS |
| 自动 | WPS 未安装或不可用，内置 LibreOffice 可用 | 使用 LibreOffice；WPS 已安装但不可用时给出简短原因 |
| 自动 | 两者都不可用 | 提示具体故障，保留文件，不进入可编辑状态 |
| WPS | WPS 可用 | 使用 WPS，即使 LibreOffice 也可用 |
| WPS | WPS 不可用 | 说明原因，提供改选自动或 LibreOffice 的入口，不悄悄替换用户选择 |
| LibreOffice | 内置 LibreOffice 可用 | 使用 LibreOffice，即使本机装有 WPS |
| LibreOffice | 内置 LibreOffice 不可用 | 提示修复运行组件，不悄悄转用 WPS |

界面只增加一个“文档引擎”选择项，并简短显示“当前：WPS”或“当前：LibreOffice”。不可用项显示原因，支持重新检测；运行组件版本、COM/UNO 细节放入诊断信息，不占据编辑主界面。用户选择保存在本机设置中，后续打开文件沿用；选择“自动”后，每次新建文档会话重新按优先级检查。

自动选择只发生在建立会话前。打开具体文档、修改、渲染或保存失败，不能为了完成操作在后台换引擎重试；缺字体和格式不支持也不能被当成静默切换的理由。保留原稿和当前版本，提供明确的手动切换入口。

用户可在文档打开后切换引擎，但切换是一次完整的会话重建：

1. 有后台作业时禁用切换。空闲时保留原稿、当前版本字节、修改历史和未保存状态，不把当前文档转换为另一种格式。
2. 用新引擎重新检查原稿和当前版本，重建范围映射、字体检查及两侧预览；不能沿用旧引擎的计划、原生位置或“已通过”状态，也不重放旧修改计划。
3. 准备和校验成功后才原子替换会话上下文并保存偏好，要求重新核对预览；失败或取消则完整保留原上下文和偏好。
4. 历史文件字节及其原始引擎记录不变。在新引擎下查看或恢复历史版本时重新解析和检查，不能混用旧缓存。切换本身不生成一次格式修改，也不丢弃尚未另存的内容。

两种引擎可能显示不同排版，因此切换需要重新预览。这是帮助用户判断结果的必要提示，不新增复杂配置面板。

| `v06_session.py` | 管理原稿、版本、渲染、失败回滚；现有 LibreOffice 路径仅面向 Linux | 抽出引擎接口，支持 Windows 便携路径，固定每个会话的引擎身份 |

历史验证记录中，LibreOffice 的格式转换路径曾出现公式或分页问题，见 [v0.6 验证记录](../verification/v06.md)。它提醒我们优先测复杂 DOC；它也不等于本次 Windows 便携版本、DOC 原格式路径已经失败或已经通过。

## 3. 内置开源引擎方案比较

WPS 是继续保留的本机可选后端，下表比较的是无可用 WPS 时所需的内置后端。

| 方案 | 对本项目的适配情况 | 决策 |
| --- | --- | --- |
| 内置 LibreOffice + UNO | 官方有 Windows 便携版、自动化接口、DOC 读写及 PDF 输出；原格式保存的实际保真仍需验证 | 首选验证路线 [S1][S2][S3][S4] |
| ONLYOFFICE Document Editor 路线 | 官方说明编辑时转换到 DOCX；其支持表的 DOC 输入输出链路不提供 DOC 回写 | 不满足当前 DOC 原格式约定，不作为主路线 [S5] |
| 仅用现有 OOXML / `python-docx` 处理 | 可复用 DOCX 结构编辑能力；本仓库这条路径没有完整分页渲染或 DOC 原格式编辑器 | 继续作为 DOCX 修改层，不能单独替代 WPS |
| 自研完整 DOC/DOCX 排版与二进制保存引擎 | 要自行承担分页、字体塑形、表格、域、公式、浮动对象和格式兼容 | 不作为本期开发范围；必要时对开源引擎做有界修复 |

不要把“免费版商业 SDK”与免费开源混为一类。若 LibreOffice 在必需的 DOC 用例上不通过，结论是该路线暂不满足发布条件，不能悄悄改为付费引擎或强制输出 DOCX。

## 4. 两种格式使用不同的修改路径

### DOCX：文序修改，选定引擎负责排版

原稿字节 → 当前结构模型与修改计划 → 当前精确补丁 → 内容和非目标属性验证 → 用本次选定的 WPS 或 LibreOffice 分别渲染原稿及结果 → 注册版本与人工核对。

不得为了获得预览而让任何排版引擎重新保存 DOCX。PDF 是临时预览产物，不回写为 DOCX。继续保护公式 XML、图片、嵌入对象及其关系，测试覆盖目标属性真实改变且非目标内容不变。

### DOC：由选定后端完成原格式编辑

WPS 分支继续复用当前原生范围编辑、DOC 保存及重新打开验证的能力。LibreOffice 分支单独建立以下链路，不能复用 WPS 的原生位置或验证结果：

原稿 DOC → UNO 读取段落、表格、字符格式与对象信息 → 生成文序修改计划 → 在独立的 DOC 副本上按原生范围应用属性 → 用 `MS Word 97` 过滤器保存 DOC → 关闭后重新读取、校验和渲染。[S2][S4]

这避免 DOC → DOCX → DOC 的编辑链路，但 LibreOffice 仍会把 DOC 导入内部模型再导出，**同扩展名不等于无损保存**。

实施时必须处理以下差异：

1. WPS 的 `Range.Start/End`、域字符和单元格结束标记不能直接对应 UNO 位置。重新建立段落、表格单元格、文本片段和原生游标的映射，校验 Unicode、重复文本、域及嵌套表格；有歧义则拒绝修改。
2. 现有 `DocumentModel` 包含 OOXML 根节点和包部件，不能要求 UNO 伪造一份 DOCX 后直接宣称兼容。提取后端无关的 `DocumentFacts`，包括文本、角色、表格关系、有效格式及只读对象清单；DOCX 保留原模型和专用验证器，DOC 使用原生锚点。
3. 公式、OLE、域和浮动对象继续只做保全，不扩大到内部编辑。修改计划遇到无法精确界定的范围或未知结构时失败，原稿与旧版本保留。
4. 保存后重新打开得到的语义信息只是一层证据。还需比较可解析的 OLE 嵌入负载、图像、关系和对象锚点，并检查非目标属性与逐页表现。不能仅让同一引擎读取自己的输出，然后把“能打开”当成保真证明。
5. DOC 的主二进制流会因合法保存而变化，不能要求整个流哈希不变；也不能用宽泛的“引擎规范化”豁免所有变化。具体允许变化必须有解释和回归用例，无法核验的结构不宣称支持。

开发验证中特设一次“无操作但强制保存”的 DOC 试验，用于暴露导入导出损失；正式产品的无操作路径仍直接返回原始字节。

## 5. 引擎接口与 Windows 交付

建议新建 `engine/` 包，按能力拆分接口，以注册表接入 `WpsEngine` 与 `LibreOfficeEngine`。UI 和会话层依赖统一接口，由选择器解析 `auto / wps / libreoffice`；后续新增后端只增加适配器和能力声明。此处“可插拔”指代码层后端可替换，本期不增加下载和执行任意第三方插件的机制，也不把业务规则放进 Office 脚本。以下均为拟新增的边界：

| 接口/数据 | 责任 |
| --- | --- |
| `resolve_engine(preference)` | 区分用户偏好与实际引擎；只在新会话或显式切换时解析，自动模式按 WPS、LibreOffice 排序 |
| `probe()` / `capabilities()` | 返回运行组件版本、可用格式、支持的修改属性与对象限制；失败给出可理解原因 |
| `inspect()` → `DocumentFacts` | 返回与源文件哈希绑定的文档事实；原生锚点仅在对应版本中有效 |
| `font_catalog()` / `check_fonts()` | 返回排版进程实际可用字体、缺失字形和可确认的替代情况 |
| `render()` | 从指定文件生成 PDF/页面，禁止覆盖或重新序列化源文件 |
| `apply_doc()` | 只接受已解析且与源版本绑定的修改计划，产出新的 DOC 候选文件 |
| 文序验证器 | 独立判断候选内容、范围和非目标属性；未通过不注册版本 |

计划、缓存和验证记录共同绑定 `source_hash + engine_id + engine_version + worker_version + font_manifest + render_profile`。引擎或字体发生变化后使旧结果失效，不能沿用 WPS 生成的“通过”状态。同一会话禁止自动切换引擎。

WPS 和 LibreOffice 都是一等运行后端，分别声明能力并验证。测试 LibreOffice 时强制选择该后端，即使开发机已安装 WPS 也不能回退；另外必须在没有 WPS 的干净机器上验收，防止开发机掩盖缺失依赖。自动模式与显式选择的行为按第 1 节单独测试。

### LibreOffice 运行组件与进程

- 先验证完整 Windows 便携分发，再考虑裁剪语言和帮助资源；不从开发机任意复制几个 DLL。使用固定版本、来源和 SHA-256 清单。[S1]
- 文序只用绝对路径启动自己的 `soffice`，指定独立 `UserInstallation`、临时工作目录和本地 UNO 命名管道；不复用用户正在使用的 Office 实例，不暴露 TCP 服务。[S3]
- 正式 Worker 首选一个随包编译交付的 C++ UNO 小程序，通过有版本的 UTF-8 JSON 协议接收文序指令。它只做 UNO 适配，不重写计划和验证。该选择避免将 `pyuno` 加载到当前 Qt/Python 进程带来的 Python ABI 和 DLL 冲突；SDK/编译器仅构建机需要。第一阶段必须证明此 Worker 和全部运行依赖可随包启动。
- 若原型使用便携包自带 Python/pyuno，必须先证实该包确实包含匹配运行时；不能依赖用户安装 Python，也不能直接把 `pyuno` 放入现有 PyInstaller 主进程。
- 用 Windows Job Object 管理自己创建的进程树，设置超时、取消和输出大小限制。异常退出只清理自己的作业，不按进程名批量结束用户的 Office。
- 打开文档时禁用宏执行、外部链接和自动更新，拒绝会要求交互的输入；禁止加载用户扩展。`headless` 自身不等于这些限制，需要验证宏、链接、对象是否确实没有被执行或刷新。[S4]
- Qt 与 LibreOffice 使用隔离的 DLL 搜索环境，延续当前构建脚本的依赖来源检查。安装目录只读，配置和作业写入用户本地应用数据目录；不注册 COM、不修改默认文件关联、不要求管理员权限。

首发仍采用整个目录的免安装 ZIP：包含 `Wenxu.exe`、Qt/Python 运行库、UNO Worker、LibreOffice 运行目录、字体和许可证。用户运行一个 EXE，但不能只拷走该 EXE。包体积、冷启动时间和峰值内存在原型阶段实测，不预报未经验证的数值。

WPS 分支继续使用本机安装提供的接口和现有自有实例管理，沿用宏/外链限制、超时和文档保护；不用 LibreOffice 的 UNO 配置控制 WPS。应用不安装或注册 WPS，两个后端的进程、临时目录及字体环境分别管理。

## 6. 字体必须由排版进程实际使用

“无需 WPS”和“任何字体都一模一样”是两个问题。推荐随包提供固定版本的 Noto CJK 等开源字体作为可选字体及基础覆盖；不会把它们改名为宋体、楷体等，也不默认替换原稿字体。Noto CJK 上游提供 OFL 许可，实际字体文件及许可随包记录。[S6]

原稿字体检查应解析实际使用的正文、表格、页眉页脚、列表、样式继承和主题字体，区分“文档声明”与“真实需要”；进一步检查相应字形覆盖和字体文件版本。当前只扫描声明名称的警告机制不能作为这一能力的完成依据。

私有字体加载的首个验证路径，是所选 LibreOffice Windows 版本的运行目录字体路径。上游 Windows 字体源码有在自身进程内从 `share/fonts/truetype` 等资源目录注册私有字体的逻辑；这是可验证的线索，尚不是我们选定发行包已经通过的证据。[S7] 不能在 Qt 进程调用 `AddFontResourceEx(..., FR_PRIVATE)` 后假定子进程也能使用，微软明确该标志仅对调用进程生效。[S8]

具体产品行为：

- 字体列表来自当前所选排版进程的有效字体集合；Qt 列表与引擎实际集合做交叉核验。切换引擎后重新检查，不能假设 LibreOffice 私有字体同时对 WPS 可见。
- 缺少实际用到的字体时，显示所缺字体，停止将当前预览判定为保真；不把未确认的替代字体隐藏起来。
- 用户补齐合法可用的原字体，或明确选择替代字体后重新核对。替代是一项显式修改，记录新版本；不声称它能恢复原来的分页和字距。
- 应用私有字体保证本工具内可用，不自动保证输出 Word 文件在其他软件、其他电脑上显示一致。本期不默认嵌入字体，也不分发从用户 WPS/Windows 安装目录收集的专有字体。

私有字体的读取位置、实际字形来源和缺字检测必须纳入第一阶段验证；仅字体下拉框中出现名称不算通过。

## 7. 如何判定“保真”

| 验证层次 | 能证明什么 | 不能推导什么 |
| --- | --- | --- |
| 原始字节一致 | 导入或无有效修改没有重写文件 | 新引擎显示一定与 WPS 一样 |
| 同引擎重复渲染一致 | 固定环境中结果稳定、比较基线可用 | 稳定的结果一定完整，公式没有一直丢失 |
| 编辑前后语义与结构检查 | 指定属性改变，可核验的内容和非目标属性得到保全 | 二进制文件所有未知结构都无损 |
| 与已确认原稿视觉基准对比 | 该样例在约定字体与环境下达到视觉要求 | 任意 Word/WPS 版本、任意文档都像素一致 |

必须使用本地已确认的原稿页面作为独立视觉基准，检查分页、文字位置、公式、图片、浮动对象和表格；不能把 LibreOffice 渲染原稿两次相等，直接标成“与原稿完全一致”。无需 WPS 的产品运行不依赖该基准；开发验收可用现有机器生成基准，私有样例及证据不外传。

字体、字号、行距或页面设置的有效修改可能合理改变分页。编辑验收同时检查“目标变化确实发生”和“非目标内容无损”，不把所有像素差异都当成错误，也不以相似度均值掩盖局部公式丢失。跨引擎基准存在未解释的缺失或排版差异时，该必需样例不得标记通过。

测试用例按风险组织：

| 编号 | 用例 | 验收证据 |
| --- | --- | --- |
| SDE-A01 | 打开、关闭、无有效修改、未指定属性 | 输出与输入哈希相同；原稿不变；无新版本或多余保存 |

| SDE-A03 | DOC 同等操作及原型强制保存 | 保存后仍为可打开 DOC；内容、对象、非目标格式与独立视觉基准一致，允许的目标排版变化有解释 |
| SDE-A04 | 旧公式、组合 WMF/EMF、OLE、域、浮动图、合并表格、页眉页脚 | 逐项对象/负载检查与全页对比；尤其覆盖此前公式缺失的本地用例 |

| SDE-A07 | 固定字体与引擎多次渲染；随后更新引擎或字体 | 重复结果稳定；旧缓存和旧验证状态失效；不同引擎的结果不混用 |
| SDE-A08 | Worker 超时、崩溃、取消、写盘失败、后台处理中操作 | 原稿与旧版本保留；不保存不完整结果；只清理自有进程；UI 恢复可用 |
| SDE-A09 | 无办公软件、无开发环境、断网、普通用户、中文路径和只读安装目录 | 实际 ZIP 解压后完成 DOC/DOCX 打开、修改、核对、另存；含宏/外链样例不执行外部动作 |
| SDE-A10 | 运行包缺文件、版本不匹配、旁路 DLL、第三方组件和私有数据检查 | 清晰报错；依赖来源/哈希及许可可追溯；包和 Git 无私有测试数据 |
| SDE-A11 | 默认自动、手动 WPS/LibreOffice；WPS 可用/未安装/接口不可用；内置组件可用/损坏；偏好持久化与重新检测 | 第 1 节选择表逐行覆盖；有 WPS 默认 WPS，无可用 WPS 默认 LibreOffice；手选结果不被自动策略覆盖 |
| SDE-A12 | 未修改或已有未保存修改时切换；切换中失败/取消；切换后查看与恢复历史版本 | 文件字节、格式和未保存内容不变；成功后重建预览、范围和校验；失败保留原会话与偏好；切换不重放修改、不生成伪修改版本 |
| SDE-A13 | 会话中引擎崩溃、文档不支持或字体缺失；当前引擎版本变化；作业进行中请求切换 | 不静默切换或沿用旧通过状态；失败保留原稿及版本；提供手动入口；处理中不能换引擎 |

自动化 CI 使用自行构造或明确可再分发的样例。用户附件存放已有忽略目录中，仅本地执行，远程只记录不含文档内容的验收结论；不能通过把测试数据编码进脚本或日志绕开此边界。

P0 若不能通过必要 DOC 用例，继续在特性分支定位开源过滤器问题，评估可维护的补丁并重跑验证。修复前不发布“完全独立且保真”的承诺，也不自动改变用户已经确认的格式约定。

## 9. 分发与维护

LibreOffice 官方以 MPL 2.0 发布，同时包含按各自许可证分发的第三方组件；随包保留对应版本的许可、版权与源码获取材料，不能只放一个笼统的“开源免费”说明。[S9] 现有 PyMuPDF 的开源路径采用 AGPL v3，也应和 PySide6、字体等一并检查发布许可与源码交付安排；进程隔离不被当作免除许可义务的依据。[S10]

新运行组件先固定版本，不静默追随最新版本。后续升级重新跑 DOC、公式、字体与干净机测试；包版本、引擎版本和验收记录一一对应。现有 [Windows LTS 约定](windows-desktop-lts.md) 保持有效，此特性通过验收并进入发布流程前不回写其“已实现能力”。

### 源码定制与上游更新

LibreOffice 的 [GitHub core 仓库](https://github.com/LibreOffice/core) 是只读镜像，供读取源码和跟踪更新；官方贡献入口是 [Gerrit](https://gerrit.libreoffice.org/)，不接收 GitHub PR。仓库说明推荐使用官方 Git bundles 获取源码。这些是仓库工作流约定，不限制我们按开源许可修改源码和维护定制版本。[S11][S12]

后续能力缺口按以下顺序处理：

1. 修改规则、范围识别、交互和验证优先放在文序核心；Office 调用与能力映射放在适配器。确认问题属于 DOC 读写、公式对象或排版引擎内部后，再修改 LibreOffice 源码。
2. 有具体引擎缺陷需要修复时，基于已选发行版的确切标签和提交，建立单独的源码维护仓库或补丁集。记录上游提交、补丁编号、最小复现、构建配置和测试结果；不把完整 LibreOffice 源码混入文序业务仓库，也不在本轮提前创建分叉。
3. 自行编译的运行组件继续通过同一个 `LibreOfficeEngine` 接口接入，不影响 WPS 后端。引擎身份包含定制补丁版本和产物哈希；替换后使旧预览缓存和校验状态失效。
4. 跟进上游时先选择候选发行版、检查自身补丁是否已被包含，再迁移仍需保留的补丁。重新构建并执行 SDE-A01–A13；通过后才更新随包版本。上游主干有新提交不触发用户端自动升级，上一版可用运行包保留供回退。
5. 希望修复进入官方版本时，通过 Gerrit 提交补丁并遵守其贡献要求；自行维护和按许可分发定制版不以官方合并为前提。对外分发时提供对应的 MPL 覆盖源码及修改，保留许可和版权声明，其他组件按各自许可处理。[S12] 用户私有稿件、页面截图和抽取内容不能作为上游补丁附件；需要复现时另行构造可公开样例。
